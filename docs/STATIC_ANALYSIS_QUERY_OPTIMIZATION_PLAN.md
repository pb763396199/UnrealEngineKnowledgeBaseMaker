# 静态闭环查询改造计划

这份计划只解决一个问题：

**以后查询一个代码对象的业务逻辑时，工具不能靠猜、不能靠全文搜索拼答案、不能靠历史总结复用答案；它必须沿着静态代码关系一直查下去。能查完就给出闭环，查不完就明确说卡在哪里。**

这里的“查完”不是证明完整业务真理，而是：

**在当前静态索引、项目约定规则和查询预算内，所有已发现的入口、调用、状态、分支、副作用、回调、外部边界和终点都被处理过。**

## 为什么要改

之前的问题不是“查不到文件”，而是查询容易停得太早：

- 找到一个中间类就当成终点。
- 找到一个看起来像中间组件的名字就以为业务链结束。
- 靠搜索结果数量判断“差不多够了”。
- 把历史问答里的经验当成事实。
- 复杂链路里漏掉注册、回调、异步、配置绑定、资源引用、状态读写。

所以新工具的目标不是写更长的总结，而是让查询过程更可靠：

```text
给一个 seed
-> 找入口
-> 找直接关系
-> 找间接关系
-> 找状态读写
-> 找分支
-> 找注册和回调
-> 找外部边界
-> 找终点
-> 判断是否闭环
```

如果中间缺索引、缺规则、候选不唯一或预算不够，工具必须明确输出原因，而不是编一个完整解释。

## 三个核心概念

### 1. 静态关系图

静态关系图是工具真正查询的东西。

它来自代码和配置的确定性扫描，包括：

- 声明关系
- 调用关系
- 继承和实现关系
- 参数和返回值流向
- 字段读写
- 条件分支
- 注册表、回调、事件绑定
- 资源引用
- 配置绑定
- 模块依赖
- 生命周期入口

这些关系必须在构建知识库时落到索引里。查询阶段只读索引，不临时用全仓搜索拼图。

### 2. 项目约定规则

原计划里的 `profile` 改名为：

**项目约定规则。**

它不是知识库记忆，不是 LLM 生成的答案，也不是每次查询自动增长的东西。

它的作用只有一个：

**把某个项目或框架里的特殊约定，翻译成通用静态关系。**

例如：

```text
某个宏 -> 这是入口
某个注册函数 -> 这里有回调边
某个配置字段 -> 绑定到某个类或资源
某个目录约定 -> 属于同一个功能域
某种命名模式 -> 标记为通用能力
某个资源 key -> 连接到加载或消费函数
```

项目约定规则可以服务一个插件、一个项目族，或者一种框架模式。

它必须是确定性的配置或规则文件。AI 可以离线帮忙提出候选，但运行时查询不能调用 AI，也不能让 AI 决定规则是否成立。

### 3. 静态闭环状态

查询结果只能落到这些状态之一：

| 状态 | 大白话含义 |
| --- | --- |
| `closed` | 在当前静态索引和规则内，已发现链路都查完了 |
| `partial` | 工具还缺索引、缺边、缺 extractor，不能说查完 |
| `blocked` | 静态分析本身无法继续，需要人工 hint 或外部事实 |
| `ambiguous` | 候选不唯一，不能自动选一个 |
| `truncated` | 深度、节点数、边数、时间或内存预算截断了 |
| `unsupported` | 当前语言、结构或规则不支持 |

`closed` 只能说“有界静态闭环完成”，不能说“完整业务逻辑已被证明”。

## AI 的位置

运行时查询不允许 AI 参与。

禁止：

- LLM 判断业务终点
- RAG 找答案
- embedding / vector search 当事实来源
- 用历史自然语言总结补全链路
- 查询阶段让 AI 猜缺失关系

允许：

- AI 离线阅读代码，建议可能的项目约定规则
- 人审查这些建议
- 把确认后的规则写成确定性配置
- 测试这些规则是否稳定、可复现

最终进入系统的必须是静态规则，不是 AI 判断。

## 规则从哪来

不同插件的规则来源分两类。

### 自动扫描得到

这些应该由工具自动生成：

- 继承、实现、override
- 函数调用
- 字段读写
- 参数和返回值流向
- 注册函数和回调表
- 生命周期函数
- 构建文件和模块依赖
- 配置文件引用
- 资源路径、软引用、字符串 key
- 宏、模板、装饰器展开后的关系

### 人工确认的项目约定

这些通常需要规则文件说明：

- 哪些宏代表入口
- 哪些注册函数代表回调边
- 哪些配置字段绑定类或资源
- 哪些字符串 key 是资源协议
- 哪些目录、模块、命名模式代表功能分组
- 哪些外部边界可以视为终点，哪些必须继续追

这部分不是“AI 必须参与”，而是“代码本身不一定能唯一证明”。AI 可以帮忙发现候选，但规则必须由人或测试确认。

## 要实现的东西

### 1. 构建阶段生成静态关系库

新增 `semantic_edges.db`，保存通用静态边。

它不是第二套独立真源。迁移关系必须明确：

- `symbol_reference_index.db` 是现有静态引用索引，第一阶段作为输入来源之一。
- `semantic_edges.db` 是闭环查询使用的规范化关系库，负责把现有引用、调用、注册、回调、配置绑定、资源引用等关系统一成一套通用边 schema。
- 构建阶段可以从 `symbol_reference_index.db` 导入已有边，但导入后必须补齐边类型、证据、快照和 extractor 信息。
- 查询阶段只读规范化后的闭环关系库；不能一部分读旧索引、一部分读新索引造成双真源。
- 运行时预检必须把闭环关系库加入必需索引集合；缺失或快照不一致时返回 `partial`，不能静默退回旧查询。

必须包含：

- 边类型
- 源节点
- 目标节点
- 文件和行号
- 证据 hash
- extractor 版本
- 构建快照 id
- 源码摘要

构建失败时不能复用旧库。必须先写临时 DB，校验通过后再替换正式 DB。

### 2. 查询阶段只读静态关系库

新增核心命令：

```text
query_static_closure <seed>
```

它和现有 `query_flow` 的关系必须明确：

- `query_flow` 保持兼容入口，继续服务旧调用方。
- 新闭环能力以 `query_static_closure` 为规范入口。
- 如果 `query_flow` 需要提供闭环语义，必须调用同一个闭环查询内核，不能复制一套遍历逻辑。
- 旧 `query_flow` 输出必须标记其边来源和闭环能力，例如 `legacy_edge_source=true` 或 `closure_status_unavailable=true`。
- Skill 文档必须说明：需要“一查到底”时使用 `query_static_closure`；`query_flow` 是兼容/局部流向查询。

它负责：

- 解析 seed
- 读取静态关系
- 展开 frontier
- 检查状态读写
- 检查分支
- 检查注册和回调
- 检查外部边界
- 检查终点
- 输出闭环状态

查询阶段不能用全文搜索临时造边。全文搜索只能作为人工回源证据。

### 3. 项目约定规则

新增规则目录，例如：

```text
rules/project_conventions/
```

每个规则包必须声明：

- 名称
- 版本
- 内容摘要
- 适用范围
- seed alias
- 能力映射
- 注册/回调/配置绑定规则
- 禁止越权的边界

同名同版本但内容不同的规则包必须被拒绝，避免缓存串线。

### 4. 审计和复现

每次闭环查询必须记录：

- seed
- 使用的规则包
- 使用的语言适配器
- 构建快照
- 源码摘要
- 查询预算
- 闭环状态
- 未展开 frontier 数量
- 缺失索引数量
- 截断原因

审计记录不能保存完整源码正文，也不能保存自然语言业务总结。

### 5. 缓存隔离

闭环查询可以缓存，但 cache key 必须包含：

- seed
- 查询预算
- 项目约定规则摘要
- 语言适配器摘要
- 构建快照
- 源码摘要
- 规则版本

任何一项变化都必须 cache miss。

## 验收标准

这次改造完成后，必须能证明：

- 工具不会把中间节点误判成终点。
- 工具不会用全文搜索结果伪造静态边。
- 工具不会用历史自然语言总结补答案。
- 缺边、缺索引、歧义、截断都会明确暴露。
- 项目约定规则不会污染通用核心。
- 不同规则包不会互相串缓存。
- 改源码或改规则后，旧缓存不会命中。
- 对同一条链路删掉关键边时，测试必须失败，不能仍然 `closed`。

## 不做什么

- 不把完整业务逻辑写成一条超大命令。
- 不让项目约定规则自动无限增长。
- 不让 AI 在运行时决定查询结果。
- 不把历史问答变成事实来源。
- 不把真实项目案例写进通用模板。
- 不用自然语言总结掩盖缺失的静态边。

## 最终目标

最终要达到的体验是：

```text
用户问：解释 X 的完整业务逻辑。

工具做：
1. 找 X 的真实入口。
2. 沿静态关系展开所有相关调用、状态、分支、注册、回调、资源、边界。
3. 明确每条链路为什么继续或为什么停止。
4. 如果闭环，输出有界静态闭环报告。
5. 如果没闭环，明确告诉用户缺什么，而不是假装完整。
```

这才是“一查到底”的价值。
